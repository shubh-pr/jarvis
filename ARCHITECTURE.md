# JARVIS

A self-hosted notification/remote-control layer for your own independently-running `claude` terminal sessions. It observes and remote-controls sessions you start yourself — it never spawns or owns agent sessions itself.

> **2026-09-23 — deliberate exception:** the line above was the founding invariant, and it's being amended rather than quietly dropped. JARVIS can now originate a session itself when you say `open <project>` for a project that isn't currently running — see the `router.ts` and `watch-project.ts` bullets below. This is scoped narrowly: it only ever launches into a directory you already ran `npm run watch-project` on (i.e. you deliberately told JARVIS about it in advance), it never runs without an explicit instruction attached, and once launched the session is tracked and behaves identically to one you started by hand. JARVIS still never *resumes* or acts on a session on its own initiative — only this one explicit, user-invoked launch.

## Backend (`src/`, Node + TypeScript, `better-sqlite3`, `ws`, `web-push`)

- **`index.ts`** — single HTTP server exposing: passcode login (`/api/login`), web-push subscribe/unsubscribe/test, three hook endpoints, and `/api/agent/resolve` for approving/denying permissions from the UI. Also upgrades to a WebSocket for live chat.
- **`hooks/routes.ts`** — handlers for Claude Code's `SessionStart`, `PermissionRequest`, and `Stop` hooks. `PermissionRequest` blocks (server timeout disabled) until you reply; `Stop` re-reads the session's transcript to pull out the assistant's last message as a "turn complete" notification.
- **`agent/permissions.ts`** — in-memory registry of pending permission requests, one per project (a new request supersedes a stale one), with a 2-minute idle nudge if you haven't answered.
- **`agent/router.ts`** — parses inbound chat replies: `status` lists active projects, YES/NO/free-text resolves a pending permission, any other text is injected into the right idle project via `claude --resume <id> --print "<text>"` (matched by project name mention, or the sole active project), and `open <project> <instruction>` either routes to that project's already-running session the same way, or — only if none is running, and only for a project already registered via `watch-project.ts` — launches a brand-new `claude --print "<instruction>"` there. Launching always requires an instruction; there's no default prompt. `open` never picks between candidates: naming two projects, or a folder name several projects share (e.g. `api` when `payments-api` and `api (id)` both live in folders called `api`), is refused with a numbered list of candidates and their paths. The list has an id; while it's open the composer switches to "Choosing which project to open" and the next message carries that id (`openChoice`), so a number, a tapped option, or a full name completes the same open — launching or routing exactly as `open <exact tag>` would, keeping the original instruction unless the answer adds one. An answer that doesn't pick exactly one option re-offers the list; a used or expired (10 min) list is refused; neither falls through to other routing. A folder name only one project has resolves to it. A message that names no project goes to the composer's reply target (`Replying to <project>`, shown above the input): it follows the newest project message on screen, tapping any message retargets it, ✕ clears it, and the client sends it with each message as `replyToSession` plus how long it had been showing. The server uses it only for free text — never to pick which request a YES/NO answers — and a project named in the message wins over it. It refuses rather than falls back if the target switched less than 1.5s before sending (or its age is missing), or if that session has ended.
- **`notifier.ts` / `push.ts`** — broadcasts events over WebSocket to connected clients, falling back to a real push notification (VAPID keys) only when nobody's connected.
- **`db.ts`** — SQLite schema: `sessions`, `messages`, `permissions`, `projects`, `push_subscriptions`, `auth_tokens`.
- **`hooks/projectTag.ts`** — derives a stable project name from a cwd, disambiguating against both known sessions and registered projects.
- **`scripts/watch-project.ts`** — CLI (`npm run watch-project <path>`) that writes the three hooks into a target project's `.claude/settings.local.json`, pointed at your local JARVIS server with a shared `HOOKS_SECRET`, and registers the project (tag + cwd) in JARVIS's own database — this registration is what makes that project a valid target for `open <project>` later, even before any session has ever run there. The path may be a single repo or a folder holding many: every git repo at or under it, at any depth (including repos nested inside repos), is registered as its own project with its own hooks — Claude Code doesn't merge hook config from an ancestor directory into a repo beneath it, so hooks must live in each repo. `node_modules`, `dist`, `.venv` and similar are skipped, and symlinks aren't followed. `--force` skips discovery and registers the path itself as one project. Tags are made unique at registration (`hooks/repoDiscovery.ts`): a repo keeps its plain folder name unless it collides (case/separator-insensitively, matching how the router reads typed names) with another repo or an already-known project; every colliding repo then takes its package name from `package.json` / `pyproject.toml` / `Cargo.toml`, else its parent folder (`api (NOBLEABLE-BE)`), adding ancestors until unique. Existing registrations keep their tags on re-runs, and a session started in a registered project's folder always takes that project's tag.

## Frontend (`public/`)

A small installable PWA (manifest + service worker + icons) — `index.html` / `app.js` / `styles.css` — a passcode-gated chat UI over the WebSocket, showing messages per project and letting you approve/deny/reply to permission prompts from your phone or browser.

## In short

You run `claude` normally in each project's terminal. JARVIS's hooks report session starts, permission requests, and turn completions to a chat-style UI, and you can approve tool calls or send follow-up instructions back — all from a single control panel instead of babysitting each terminal.
