# JARVIS

A self-hosted notification/remote-control layer for your own independently-running `claude` terminal sessions. It observes and remote-controls sessions you start yourself — it never spawns or owns agent sessions itself.

> **2026-09-23 — deliberate exception:** the line above was the founding invariant, and it's being amended rather than quietly dropped. JARVIS can now originate a session itself when you say `open <project>` for a project that isn't currently running — see the `router.ts` and `watch-project.ts` bullets below. This is scoped narrowly: it only ever launches into a directory you already ran `npm run watch-project` on (i.e. you deliberately told JARVIS about it in advance), it never runs without an explicit instruction attached, and once launched the session is tracked and behaves identically to one you started by hand. JARVIS still never *resumes* or acts on a session on its own initiative — only this one explicit, user-invoked launch.

## Backend (`src/`, Node + TypeScript, `better-sqlite3`, `ws`, `web-push`)

- **`index.ts`** — single HTTP server exposing: passcode login (`/api/login`), web-push subscribe/unsubscribe/test, three hook endpoints, and `/api/agent/resolve` for approving/denying permissions from the UI. Also upgrades to a WebSocket for live chat.
- **`hooks/routes.ts`** — handlers for Claude Code's `SessionStart`, `PermissionRequest`, and `Stop` hooks. `PermissionRequest` blocks (server timeout disabled) until you reply; `Stop` re-reads the session's transcript to pull out the assistant's last message as a "turn complete" notification. Every other request is shown in plain English (`agent/describe.ts`): the headline is the one-line description Claude writes for each Bash command (or a gist like "Edit src/app.ts" for other tools); under it, Jarvis's own tags from reading the actual command — deletes files, writes files, pushes to a remote, changes git history, installs packages, goes online, runs a script — and the exact command, one line, tap to expand. The description is Claude's claim, so the tags and command are always shown with it. Claude's `AskUserQuestion` tool also arrives as a PermissionRequest, but it's a multiple-choice question, not a run/don't-run gate (`agent/questions.ts`): the request carries its questions, and the PWA shows a question card — header, question, and each option's label and description — instead of Approve/Deny. An answer is returned as an allow with `updatedInput.answers` (keyed by question text; an option label, an array of labels for multi-select, or free text) — verified end to end in an interactive session: the terminal shows `question → answer` and Claude receives it. A typed reply to a question is its answer (option number, exact label, or free text; single-question requests only). A generic Approve or "yes" on a question is refused, because an allow without answers only moves the question to the terminal, where Claude Code shows it and waits; that remains available as the card's explicit "Answer in terminal instead". Dismiss denies it without interrupting Claude. `AskUserQuestion` doesn't exist in `--print` runs, so these only ever come from interactive sessions.
- **`agent/permissions.ts`** — in-memory registry of pending permission requests, one per project (a new request supersedes a stale one), with a 2-minute idle nudge if you haven't answered.
- **`agent/router.ts`** — parses inbound chat replies: `status` lists active projects — one line per project, from live state only (a pending request, or in-memory turn tracking: waiting on you / starting / working / idle), never the stored session status, which goes stale when a turn ends without a Stop; older idle sessions fold into a count, and two sessions genuinely active in one project are both listed — YES/NO/free-text resolves a pending permission, any other text is injected into the right idle project via `claude --resume <id> --print "<text>"` (matched by project name mention, or the sole active project), and `open <project> <instruction>` either routes to that project's already-running session the same way, or — only if none is running, and only for a project already registered via `watch-project.ts` — launches a brand-new `claude --print "<instruction>"` there. Launching always requires an instruction; there's no default prompt. A launch picks its own session ID (`claude --session-id <uuid> --print …`), so the session is registered — as `starting` — the moment it's spawned; the SessionStart hook can't be relied on for this (it hasn't fired for Jarvis in any mode). More generally, a session is *busy* from the start of a turn until its Stop hook, and nothing new is ever sent into a busy session: a turn Jarvis starts (launch or resume) is marked busy the instant it's spawned; a turn started anywhere else is marked by the `UserPromptSubmit` hook (verified to fire with the session ID for new and resumed turns) or by a permission request. A second `open`, a reply, or a plain instruction for a busy session is queued, and everything queued goes in as one resumed turn when Stop arrives. Each queued message has an ID; the server broadcasts the queue (`{type:"queue"}`, also sent on connect) and the PWA shows it as a "Waiting to send" panel with the actual text and a ✕ per message (`{type:"unqueue", queueItemId}`); `status` lists the texts too. The server's queue is the source of truth: only what's still in it is sent, and removing a message that has already gone in is refused rather than reported as removed. Answering a pending permission request is unaffected — that's a reply inside the turn, not a new one. If a Jarvis-spawned process exits without a Stop, the session is free again: a first launch is closed (queued messages reported as not sent); a resumed turn gets its queued messages delivered, with a note. Claude Code sends no Stop for an interrupted turn, which can't be told apart from a long quiet one, so Jarvis never assumes: after `BUSY_NUDGE_MS` (default 10 min) with no hook activity and messages waiting, it says so once, and `send now [project]` delivers them anyway. Busy state is in memory; after a restart sessions start out free. `open` never picks between candidates: naming two projects, or a folder name several projects share (e.g. `api` when `payments-api` and `api (id)` both live in folders called `api`), is refused with a numbered list of candidates and their paths. The list has an id; while it's open the composer switches to "Choosing which project to open" and the next message carries that id (`openChoice`), so a number, a tapped option, or a full name completes the same open — launching or routing exactly as `open <exact tag>` would, keeping the original instruction unless the answer adds one. An answer that doesn't pick exactly one option re-offers the list; a used or expired (10 min) list is refused; neither falls through to other routing. A folder name only one project has resolves to it. A message that names no project goes to the composer's reply target (`Replying to <project>`, shown above the input): it follows the newest project message on screen, tapping any message retargets it, ✕ clears it, and the client sends it with each message as `replyToSession` plus how long it had been showing. The server uses it only for free text — never to pick which request a YES/NO answers — and a project named in the message wins over it. It refuses rather than falls back if the target switched less than 1.5s before sending (or its age is missing), or if that session has ended.
- **`notifier.ts` / `push.ts`** — broadcasts events over WebSocket to connected clients, falling back to a real push notification (VAPID keys) only when nobody's connected.
- **`db.ts`** — SQLite schema: `sessions`, `messages`, `permissions`, `projects`, `push_subscriptions`, `auth_tokens`.
- **`hooks/projectTag.ts`** — derives a stable project name from a cwd, disambiguating against both known sessions and registered projects.
- **`scripts/watch-project.ts`** — CLI (`npm run watch-project <path>`) that writes the three hooks into a target project's `.claude/settings.local.json`, pointed at your local JARVIS server with a shared `HOOKS_SECRET`, and registers the project (tag + cwd) in JARVIS's own database — this registration is what makes that project a valid target for `open <project>` later, even before any session has ever run there. The path may be a single repo or a folder holding many: every git repo at or under it, at any depth (including repos nested inside repos), is registered as its own project with its own hooks — Claude Code doesn't merge hook config from an ancestor directory into a repo beneath it, so hooks must live in each repo. `node_modules`, `dist`, `.venv` and similar are skipped, and symlinks aren't followed. `--force` skips discovery and registers the path itself as one project. Tags are made unique at registration (`hooks/repoDiscovery.ts`): a repo keeps its plain folder name unless it collides (case/separator-insensitively, matching how the router reads typed names) with another repo or an already-known project; every colliding repo then takes its package name from `package.json` / `pyproject.toml` / `Cargo.toml`, else its parent folder (`api (NOBLEABLE-BE)`), adding ancestors until unique. Existing registrations keep their tags on re-runs, and a session started in a registered project's folder always takes that project's tag. Each repo also gets default Claude Code permission rules (`hooks/permissionDefaults.ts`, skip with `--no-permissions`): `git -C <exact repo path> status/log/diff/show` and the list-only forms run unprompted, as do the repo's offline build/test commands (`./mvnw -o compile|test|package`, `mvn -o …`, or `npm test` / `npm run build` when those scripts exist — exact commands, no wildcards); state-changing git, git's `--output` flag, installs, `npx`, `rm`, `curl` and `wget` are `ask` rules, which Claude Code checks before allow rules. The path is never wildcarded because `git -C * log` would also match `git -C x -c core.pager=<cmd> log`. Allowed commands never reach the PermissionRequest hook. Existing rules are kept and re-runs only add what's missing.

- **`agent/search.ts`** — search across all history (`/api/search?q=&key=`): an FTS5 index over the messages table (porter stemming, kept in step by triggers, built from existing history on first start). Every stored message is searchable — your messages and terminal prompts, Claude's replies, permission requests (headline and command), questions. Words, not meaning: stemming links "implementing"/"implementation" but not synonyms. All words must match, the last as a prefix; under 5 conversations, ones matching only some words are returned separately as partial matches. One result per conversation block — its best-matching message with the match highlighted in context, plus how many others in it matched — ranked by bm25 relevance, recency only breaking ties. Typed text is always quoted into terms, so FTS syntax can't cause errors. `?key=` scopes to one project. The PWA's Search opens a panel (all projects, or only the open one); tapping a result opens that conversation scrolled to that message.
- **`agent/history.ts`** — per-project conversation history. A project is its full path (a session's starting folder), never its display name, so same-named repos never share history. Messages are grouped into blocks of continuous work, split at 2 hours of quiet, computed from timestamps when read; a block that runs past midnight stays whole, and its date is a label and filter. Block titles come from what's there: your first message (PWA or terminal), else the first request's plain-English headline, else Claude's first sentence. Served at `/api/projects`, `/api/projects/blocks?key=&from=&to=` and `/api/projects/messages?key=&from=&to=` (login required). A session's folder is fixed at first sight — the `cwd` in later hook calls follows Claude's `cd`s — and on startup any stored folder that disagrees with the session's transcript (whose first entry records where it started) is corrected. Prompts typed in a terminal are recorded from `UserPromptSubmit`; ones Jarvis sent aren't recorded twice. Live events, cards and acks carry `projectKey`.

## Frontend (`public/`)

A small installable PWA (manifest + service worker + icons) — `index.html` / `app.js` / `styles.css` — passcode-gated, over the WebSocket. Home is the list of projects (by path, with last activity, waiting and unread badges); opening one shows its latest block of work, live, and History browses earlier blocks grouped by day with date filters. A strip at the top of every screen shows any project waiting on you. `open <project> …` and a tapped notification land in that project. Approve/deny/answer and reply to permission prompts from your phone or browser.

## In short

You run `claude` normally in each project's terminal. JARVIS's hooks report session starts, permission requests, and turn completions to a chat-style UI, and you can approve tool calls or send follow-up instructions back — all from a single control panel instead of babysitting each terminal.
